# Meridian Supply Co. — the book's dataset

Every example in *AI Engineering from Zero to One* runs against one synthetic company. That is
deliberate: disconnected toy examples are why people finish a technical book without intuition.

Meridian is a mid-sized industrial and janitorial supplies distributor operating in five US
regions. It is **entirely fictional**, generated by `generate.py`, and contains **no real
personal data of any kind**.

## Generate it

```bash
python3 generate.py          # ~40 seconds, stdlib only, no network
python3 verify.py            # proves the planted facts are present and consistent
python3 render.py            # optional: PDFs, including one real scan (needs pandoc + tectonic + poppler)
```

Output lands in `data/meridian/`. The generator is seeded, so two people get byte-identical
output — which is what lets the book quote exact figures.

## What you get

| Path | Contents |
|---|---|
| `warehouse/meridian.db` | SQLite: regions, suppliers, customers, products, orders, order lines, and a `v_sales` view |
| `warehouse/transactions.csv` | The same sales data denormalized, for Chapter 2 |
| `documents/quarterly-reviews/` | 12 business reviews, 2023 Q1 – 2025 Q4 |
| `documents/contracts/` | 40 supplier agreements — **8 are near-identical by design** |
| `documents/tickets/tickets.jsonl` | 600 support tickets: short, misspelled, some not in English |
| `documents/awkward/` | 6 documents that are hard to parse on purpose |
| `documents/poisoned/` | 4 documents carrying real prompt-injection payloads |
| `manifest.json` | Counts, the planted facts, and every quarter's totals |

## The one rule that makes this dataset useful

**The documents are written from the warehouse, not beside it.** Every figure quoted in a
quarterly review is computed from the generated transactions. `verify.py` checks all twelve
against SQL and fails if any disagree by more than a dollar.

That is what makes questions like *"Why did Midwest revenue fall in 2024 Q3?"* interesting:
the warehouse knows the **size** of the fall and not the cause; the documents state the
**cause** and not the size. Answering it needs both.

## The planted facts

| Quarter | What happened | Where it shows |
|---|---|---|
| 2024 Q2 | The Sanitation category launched | A fifth category appears in the data |
| 2024 Q3 | Halloway Group, the Midwest's largest account, did not renew | Midwest revenue falls 53% |
| 2024 Q4 | A batch defect in Pemberton Mills cloths | Quality tickets spike 3.5× |
| 2025 Q1 | Voss Industrial raised unit costs 12% | Voss margin falls 34.6% → 27.4% |

There is also one **confound** that no document explains: Voss margin *rises* in 2024 Q2,
because the Sanitation launch shifted its product mix, not because of pricing. Chapter 15
uses it.

## The awkward documents

These matter more than the clean ones. Parsing is where real retrieval projects die.

1. **Two-column newsletter** — columns, run-together words, a ligature and a hyphenated break
2. **Rotated table** — a three-row header and right-aligned numeric text
3. **400-item appendix** — about 29,000 tokens: fits a window, too costly to send whole (Chapter 10)
4. **Header/footer noise** — the same banner on all 24 pages, which poisons chunking
5. **A form** — labels and values, no prose for an embedding model to grip
6. **A genuine scan** — rendered, rasterized, and reassembled, so `pdftotext` returns
   **zero characters**. It needs a vision model. `render.py` asserts this and fails if a
   text layer ever appears.

## The poisoned documents

Four files carry deliberate indirect prompt-injection payloads: an instruction override, an
exfiltration attempt through a Markdown image URL, an attempt to make an agent call a tool it
should not, and — the one that matters — an exfiltration disguised as an ordinary house
formatting convention, which claims no authority and is therefore missed by defences tuned to
detect assertiveness. They are safe to read and safe to index. They are dangerous only to a
system that treats retrieved text as instructions, which is the lesson of Chapter 29.
